# 001. 워크숍 예약 시스템 — 트랜잭션 원자성

> **상태:** 미완료 (구현 및 검증 전)
>
> **기술 스택:** Java 21 · Spring Boot · Spring Data JPA · PostgreSQL
>
> **핵심 학습:** `@Transactional`, JPA Dirty Checking, 트랜잭션 원자성, 예외 처리, PostgreSQL 통합 테스트

## 1. 과제 개요

### 비즈니스 시나리오

온라인 워크숍 예약 서비스의 예약 API를 구현한다.

각 워크숍은 정해진 잔여석을 보유하며, 사용자는 원하는 워크숍에 한 자리를 예약할 수 있다.

예약 요청이 성공하면 다음 두 작업이 수행되어야 한다.

1. 예약 내역(Reservation) 1건 생성
2. 해당 워크숍(Workshop)의 잔여석 1개 차감

두 작업은 반드시 **하나의 트랜잭션으로 처리**되어야 한다.

예약 내역 저장이나 잔여석 차감 중 어느 하나라도 실패하면 전체 작업을 롤백하여 데이터 일관성을 보장해야 한다.

### 학습 목표

- Spring의 선언적 트랜잭션을 이용해 데이터 변경의 원자성을 보장한다.
- JPA 변경 감지(Dirty Checking)를 이용해 엔티티 상태를 변경한다.
- 비즈니스 예외를 적절한 HTTP 상태 코드로 변환한다.
- 실제 PostgreSQL 환경에서 트랜잭션의 커밋과 롤백을 검증한다.

---

## 2. 기능 요구사항

### FR-01. 워크숍 조회

- 요청받은 `workshopId`로 워크숍을 조회한다.
- 존재하지 않는 워크숍이라면 `404 Not Found`를 반환한다.
- 실패한 요청은 데이터베이스 상태를 변경하지 않는다.

### FR-02. 예약 가능 여부 검증

- 워크숍의 잔여석을 확인한다.
- 잔여석이 0이라면 `409 Conflict`를 반환한다.
- 예약 내역을 생성하거나 잔여석을 변경하지 않는다.

### FR-03. 예약 생성

- 예약 가능한 워크숍에 대해 사용자 예약 내역 1건을 생성한다.
- 예약은 해당 워크숍과 사용자 식별자를 포함해야 한다.
- 정상 처리 시 `201 Created`를 반환한다.

### FR-04. 잔여석 차감

- 예약이 성공하면 해당 워크숍의 잔여석을 정확히 1 감소시킨다.
- 잔여석 변경에는 JPA Dirty Checking을 사용한다.
- 잔여석 변경만을 위한 직접 UPDATE 쿼리는 사용하지 않는다.

### FR-05. 트랜잭션 원자성

- 예약 생성과 잔여석 차감은 하나의 트랜잭션에서 처리한다.
- 모든 작업이 성공한 경우에만 변경 내용을 커밋한다.
- 처리 중 실패하면 두 데이터의 변경을 모두 롤백한다.
- 롤백 이후 예약 내역과 잔여석은 요청 이전 상태를 유지해야 한다.

## 3. API 명세

### 워크숍 예약

`POST /workshops/{workshopId}/reservations`

**Path Parameter**

| 이름 | 타입 | 설명 |
|---|---|---|
| workshopId | Long | 예약할 워크숍 식별자 |

**Request Body**

```json
{
  "userId": 1001
}
```

| 이름 | 타입 | 설명 |
|---|---|---|
| userId | Long | 예약을 요청한 사용자 식별자 |

**Response**

| HTTP Status | 상황 |
|---|---|
| 201 Created | 예약 성공 |
| 404 Not Found | 워크숍이 존재하지 않음 |
| 409 Conflict | 잔여석 부족 |
| 500 Internal Server Error | 예상하지 못한 서버 오류 |

성공 응답 본문과 오류 응답 형식은 직접 설계한다.

## 4. 기술적 제약사항

### 필수 기술

- Java 21
- Spring Boot
- Spring Data JPA / Hibernate
- PostgreSQL
- JUnit 기반 테스트

### 구현 제약

1. Spring의 선언적 트랜잭션을 사용한다.
2. 잔여석 차감은 JPA 변경 감지로 처리한다.
3. 예약 정보는 실제 PostgreSQL에 저장한다.
4. 트랜잭션 실패 시 부분적인 데이터 변경이 남아서는 안 된다.
5. 통합 테스트는 H2가 아닌 실제 PostgreSQL을 사용한다.
6. 테스트에서 최종 DB 상태는 요청 처리 이후 독립된 트랜잭션으로 확인한다.

### 이번 과제에서 제외하는 범위

- 동시 예약 요청 처리
- 낙관적 락 및 비관적 락
- 분산락
- 사용자 인증 및 인가
- 결제 처리
- 예약 취소 및 환불
- 동일 사용자 중복 예약 제한

동시성 제어는 후속 과제 002에서 다룬다.

## 5. 완료 기준

모든 시나리오는 실제 PostgreSQL을 사용하는 통합 테스트로 검증한다.

### T01. 정상 예약

**Given**
- 워크숍이 존재한다.
- 잔여석은 1개이다.
- 해당 워크숍의 기존 예약은 0건이다.

**When**
- 사용자가 예약 API를 호출한다.

**Then**
- HTTP 201을 반환한다.
- 예약 내역이 정확히 1건 생성된다.
- 잔여석이 0으로 변경된다.
- 요청 종료 후 DB를 재조회해 결과를 확인할 수 있다.

### T02. 존재하지 않는 워크숍

**Given**
- 요청한 `workshopId`에 해당하는 워크숍이 존재하지 않는다.

**When**
- 예약 API를 호출한다.

**Then**
- HTTP 404를 반환한다.
- 예약 내역이 생성되지 않는다.
- 기존 DB 데이터는 변경되지 않는다.

### T03. 잔여석 부족

**Given**
- 워크숍이 존재한다.
- 잔여석이 0개이다.

**When**
- 예약 API를 호출한다.

**Then**
- HTTP 409를 반환한다.
- 예약 내역이 생성되지 않는다.
- 기존 예약 건수와 잔여석이 유지된다.

### T04. 처리 중 예외 발생 및 롤백

**Given**
- 워크숍이 존재하며 예약 가능한 잔여석이 있다.
- 트랜잭션 처리 중 DB에 실제 쓰기가 발생한 이후 실패하는 상황을 재현한다.

**When**
- 예약 처리 중 예외가 발생한다.

**Then**
- 트랜잭션이 롤백된다.
- 요청 처리 종료 후 별도 트랜잭션에서 DB를 재조회한다.
- 신규 예약 내역이 남아 있지 않다.
- 잔여석이 요청 이전 값으로 유지된다.
- 부분적으로 커밋된 데이터가 존재하지 않는다.

**검증 조건:** 단순히 예외 발생 여부만 확인하는 것은 충분하지 않다. 실제 DB 쓰기 이후 실패했음을 재현하고, 최종 데이터 상태를 검증해야 한다.

## 10. 후속 과제

**002. 워크숍 마지막 자리 동시 예약**

001에서 구현한 예약 기능을 기반으로, 다수 사용자가 동시에 예약을 요청하는 상황에서 발생하는 데이터 정합성 문제를 해결한다.

- 잔여석 1개에 동시 요청 10건
- 잔여석 3개에 동시 요청 10건
- 잔여석 3개에 동시 요청 2건
- 동시성 제어 방식 직접 선택 및 검증

001 모듈은 독립적으로 보존하고, 후속 과제에서 코드를 확장하여 동시성 제어 도입 전후를 비교한다.
